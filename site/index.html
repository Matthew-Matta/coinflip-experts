When rounding picks the expert

Matthew Matta

Serving the same prompts in a batch of 8 instead of 1 changed which experts ran for 7.25% of tokens in an average layer.

OLMoE, a Mixture-of-Experts model, sends each token to 8 of its 64 experts. When the 8th and 9th are almost tied, tiny rounding differences decide which one runs. I measured how often that happens during prefill in a real serving engine, built a tool that traces a routing change to the operation behind it, and turned the results into practical requirements for matching a reference model.

1. The coin flip

In an MoE model like OLMoE-1B-7B, a small router scores all 64 experts for each token and keeps the top 8. That is a hard cut. Expert #8 runs and expert #9 does not, no matter how close their scores are.

Usually the gap is large, but some tokens sit right on the line. For those, the winner depends on things that normally never matter: the order numbers are added in, how many bits the hardware keeps, how a sort breaks ties. Change the chip and you can change the expert.

2. It happens in real serving

I ran OLMoE in SGLang, a widely used serving engine, on one NVIDIA L4 GPU. I sent the same 200 prompts at batch sizes 1, 8 and 32 and recorded which experts every token used in each of the 16 layers during prefill.1

Running the same setup twice changed nothing. Going from batch 1 to batch 8 changed the experts for 7.25% of tokens in an average layer (95% CI 7.03–7.48%). Batch 32 gave 7.21%. In 97.9% of those changes exactly one expert was swapped, which is what near-ties flipping looks like.2

3. Tracing the cause

When a ported model's expert choices change, the hard part is finding which operation did it. I built routediff to do that in three steps:

  1. Learn normal noise. Run harmless variants, like adding numbers in a different order, and record how much each operation's output moves. Twice that is the allowed difference.
  2. Find the suspect. Save every intermediate result from both versions. The first operation over its allowed difference is the suspect.
  3. Test the repair. Paste the reference's result into that operation and rerun. If the expert choices or the output come back, that operation is where the fix belongs.3

I tested it on my own C++ version of OLMoE's MoE layer, with bugs planted by a script I couldn't see. routediff found and pinpointed 44 of 44 planted bugs, with 0 false alarms in 32 clean runs.4 Figure 3 shows one of them.

The most useful catch was my own bug. My first C++ version added up one normalisation step in a different order from PyTorch. routediff's normal mode correctly called it harmless, since no expert choices changed; its strict mode pointed straight at the step I had found by hand. The port picks the same experts as PyTorch and is just as accurate against a high-precision reference, but it failed the stricter element-by-element test I set in advance, and I report that.5

Porting a second model was quick. With the same tools I brought a Qwen3-30B-A3B MoE layer to C++ in about 15 minutes, and it picks the same experts as PyTorch on all 1,361 test tokens. routediff now runs on four backends: my C++ port, PyTorch on CPU, Apple's GPU and an NVIDIA L4. I also wrote an ARM NEON (SIMD) path for the port. It is 2.6–2.9× faster than plain C++ doing the same additions in the same order, and its adding order changed no expert choices.6

4. What a port must get right

To pick the same experts as the reference model, a port on new hardware needs:

  • Enough bits when adding up. The router's running sum needed at least 18 bits of precision and the projection feeding it 19. fp32 has 23; rounding the router's sum to bf16's 7 flipped 13% of routes. routediff raises the alarm from 21 bits down, before routing breaks (Figure 4).7
  • fp32 for the cross-chip sum feeding the router. When I emulated splitting the layer across chips, fp32 changed no routes at any chip count and bf16 did.8 Against real NVIDIA NCCL the emulation matched exactly on 2 GPUs. On 4 it didn't, so I worked out adding orders that reproduce all 1.2M of NCCL's output values exactly: tree adds GPUs 2 → 3 → 1 → 0, and ring uses 8 blocks with a rotating start.9
  • A written tie rule. As the box at the top shows, platforms break exact ties differently. The chip or kernel spec should say which expert wins.

5. Limits and related work

  • One model in depth (OLMoE-1B-7B, layers 0 and 7) plus one Qwen3-30B-A3B layer, and no attention in my C++ layer.
  • The planted bugs are large. The test shows the method works, not how small a bug it can catch.
  • The serving measurement is prefill only, on one GPU type and one model, and doesn't say which operation caused each flip.
  • I didn't measure whether these route changes affect generated answers or task quality.
  • The larger collective sweep is emulation, with separate real checks at 2 and 4 GPUs; this is not a production runtime or a multi-node benchmark.

This builds on others' work:

  • arXiv 2607.28097 showed adding order and precision change MoE routes and proposed a numerical compatibility contract; mine adds measured thresholds.
  • arXiv 2608.11212 studies OLMoE route flips under simulated 4-bit KV-cache quantization.
  • R3 (arXiv 2510.11370) and Miles (arXiv 2609.08368) replay the serving engine's expert choices in RL training.
  • Fireworks AI's blog post (2026-09-30) describes near-ties flipping experts in production RL.
  • Thinking Machines' batch-invariant kernels and SGLang's deterministic mode remove batch dependence; msprobe, Polygraphy and DeepView find the first tensor that differs between backends.

Why it matters

Which experts run is a yes-or-no output, and it can change even when every number looks almost right. So a port should be checked on expert choices, not just on errors, and the hardware should keep enough bits in the router's sums and follow a written tie rule. routediff and the numerics contract turn those checks into something you can run.
