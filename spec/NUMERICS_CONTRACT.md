# Numerics contract for porting an MoE layer (draft)

What an accelerator port of an OLMoE-style MoE block must guarantee so that expert routing matches the reference, with
each requirement tied to a number measured in this repository. The idea of a numerical compatibility contract between
a model and the hardware that runs it comes from arXiv 2607.28097; this draft adds measured thresholds and the
evidence behind each line.

**Scope and limits.** OLMoE-1B-7B-0924, MoE blocks of layers 0 and 7, 32 prompts (1,348 tokens per layer; 664 held-out
evaluation tokens), PyTorch CPU (transformers 5.12.1, eager experts) as the reference, fp64 oracle as ground truth.
Anything about more than one chip is **emulation** of a stated summation order, not a measurement of an interconnect;
it was checked against real NCCL at 2 ranks (bit-exact) and 4 ranks (NCCL's order recovered post hoc; see R1), on L4 GPUs over shared
memory (PCIe topology not verified). Numbers are descriptive unless
marked as a preregistered result (PREREG.md). "Route flip" = the set of top-8 experts differs for a token.

## Requirements

|---|---|---|---|
| R1 | **Router-input all-reduce in fp32.** The cross-chip sum that produces the router input (row-parallel `o_proj`) must accumulate and travel in fp32. | fp32 wire: 0 route flips at every emulated chip count 2-64, ring and tree, both layers. bf16 wire, ring: layer 0 flips rise from 10 to 49 of 1,348 tokens (0.7% to 3.6%) from 2 to 64 chips; layer 7 from 0 to 8. Preregistered H4: PASS (Spearman rho 0.90 / 0.88). In a bf16 model *(exploratory)*: at 2-8 emulated chips a bf16 wire re-decides 5-19 of 1,348 tokens relative to the single-chip bf16 model, and an fp32 wire changes none. *Emulation of the stated sum order* (`REDUCTION_ORDER.md`): real NCCL 2.29.7 matches it bit-exactly at 2 ranks. At 4 ranks (4x L4, shared-memory transport; no PCIe/NVLink claim) NCCL's order, recovered post hoc and matching every element in fp32 and bf16: Tree = sequential sum in rank order 2, 3, 1, 0; Ring = 8 equal contiguous blocks, block b starting at rank (b+1) mod 4 and summing cyclically (1230, 2301, 3012, 0123, repeated). No single fixed order explains more than ~69% of Ring elements. **Implication: a collective emulator must model the per-chunk rotation of the start rank, not a single rank order**; this repo's emulator uses the same rotation (1230, 2301, 3012, 0123 at n = 4) but applies it by position within each token's output vector rather than over contiguous blocks of the flattened batch tensor, and its tree is a pairwise sum in rank order 0123 rather than NCCL's sequential 2310, so its chip-count trends for n >= 4 are not NCCL's exact numbers. | `findings/h4-collective-sweep-fp32/`, `findings/h4-collective-sweep-bf16-exploratory/`, `findings/nccl-validation/` (`order-followup/`) |
| R2 | **If bf16 must be used on the wire, reduce as a tree, not a ring.** | bf16 tree at 64 chips: 23 (layer 0) / 5 (layer 7) flipped tokens vs 49 / 8 for ring; down-projection output error 3.3e-3 (tree) vs 7.6e-3 (ring) relative L2 at 64 chips, layer 0. *Emulation.* | `findings/h4-collective-sweep-fp32/` |
| R3 | **Expert down-projection all-reduce: fp32 keeps output error at the single-chip level.** It cannot change this block's routes, but it feeds the next layer's router. | fp32 wire: relative L2 vs oracle ~1.1e-6 at every chip count (single chip: 1.18e-6); bf16 wire: 1.9e-3 at 2 chips rising to 7.6e-3 (ring) at 64. 0 route flips in this block, as expected. *Emulation.* | `findings/h4-collective-sweep-fp32/` |
| R4 | **Top-k tie semantics are an ISA-level requirement:** the top-k instruction (or kernel) must define which expert wins an exact tie (e.g. "lower expert id wins"), and the port must implement that rule exactly instead of inheriting a sort algorithm's behaviour. | bf16 router logits produce exact ties between the 8th and 9th expert on 13 (layer 0) and 25 (layer 7) of 1,348 OLMoE tokens, and on **124 of 1,361 (9.1%) Qwen3-30B-A3B layer-0 tokens** (exploratory). PyTorch MPS and the C++ port (lower id) agree on 38/38 OLMoE ties; PyTorch CPU disagrees on 27/38. PyTorch CPU on macOS is reproduced exactly (1,348/1,348 tokens) by its `nth_element` top-k with a value-only comparator (libc++), so it follows a selection algorithm, not a stated rule. **Tie behaviour is platform-dependent:** the Linux build of the same torch 2.14.1, given the same probabilities, picks the same set as macOS on only 19/38 ties (CI run 38991546221). On Qwen3 all 65 bf16 route mismatches between the port and PyTorch CPU are ties. fp32 logits: 0 ties on either model. Ties also make bf16 output tolerances meaningless: calibrated on all tokens, the bf16 output tolerance is 482 scaled ULP; on route-matched tokens it is 10. | `findings/backend-pairs-v1/` (`bf16_ties.json`, `torch_topk_emulation.cpp`); `findings/topk-portability/`; `findings/qwen3-port/`; `findings/bf16-tolerances/` |
| R5 | **Router accumulator >= 18 mantissa bits; o_proj accumulator (router input) >= 19** (8-bit exponent; fp32's 23 meets both). RMSNorm, expert and combine accumulators do not affect this block's routes even at bf16 width. | Planted bf16 router accumulator (blinded evaluation): 33 of 204 evaluation tokens changed experts; output relative L2 7.6e-2 (median over 4 cases). | R6 | **Router output (gate) dtype and softmax: as the reference specifies (softmax in fp32).** | Planted lower-precision gate output: 4 / 190 tokens changed experts, output relative L2 1.8e-2 (median over 4 cases). | R7 | **Attention output projection (`o_proj`) accumulates in fp32** (minimum width: R5). | Planted lower-precision `o_proj` accumulator: 12 / 148 tokens changed experts, output relative L2 3.6e-2 (median over 4 cases). | `findings/routediff-eval-real-v2/per_bug_type.json` |
| R8 | **Combine (weighted sum of the 8 expert outputs) accumulates in fp32 and rounds once.** | transformers' `grouped_mm` path (fp32 sum, one rounding) is closer to the fp64 oracle than the eager path (bf16 buffer, rounding after every expert) on 96.9% (layer 0) and 99.5% (layer 7) of tokens: relative error 4.75e-3 vs 5.72e-3 (layer 0), 95% CI of the paired difference excludes 0. | R10 | **Elementwise transcendentals (`exp` in softmax and SiLU) within a few ULP of correctly rounded.** | PyTorch's vectorised `exp` differs from correctly rounded by up to 5 ULP (softmax) and 2 ULP (SiLU activation); the 2-ULP activation difference amplifies to ~80 ULP p99 at the down projection where outputs nearly cancel, while relative L2 vs fp64 stays 1.06-1.26e-6 for both the port and PyTorch (they differ from each other by 1.2-2.1e-7) and routes are unchanged. | `findings/m2-postfix-validation/` (`oracle_comparison.json`) |
| R11 | **The renormalisation sum of top-k weights (`norm_topk_prob` models) is a reduction like any other; its order belongs to the reordering budget, not to "exact" semantics.** | Qwen3-30B-A3B layer 0 (exploratory): given identical probabilities, the renormalised weights match PyTorch CPU bit-exactly on 727 / 895 / 1,361 of 1,361 tokens for sequential / pairwise / PyTorch's 4-lane cascade order. | R12 | **Serving: if routing must not depend on batch composition, serving kernels must be batch-invariant.** | SGLang 0.5.21 (+ backport of #40980), OLMoE bf16 prefill on one L4, 200 prompts x 16 layers: batch 8 vs batch 1 changes the expert set of 7.25% of token-layers (95% prompt-cluster CI 7.03-7.48%); batch 32: 7.21%; the same configuration twice (R0): 0 of 1,059,312. ## Not covered
Attention, KV cache and RoPE numerics (not in the C++ block); decode-phase routing; real multi-chip interconnects;
layers other than 0 and 7 (plus one exploratory Qwen3 layer). The budget in R9 is calibrated in fp32 and does not apply
to bf16 values; exploratory bf16 tolerances are in `findings/bf16-tolerances/` (their output tolerance is set by tie
tokens, see R4).

## Evidence notes
- Planted-bug effects (R5-R8) aggregate the sealed routediff reports of the blinded real-v2 evaluation per bug type
  (4 cases each, evaluation prompts only), computed after scoring by `findings/routediff-eval-real-v2/per_bug_type.py`
  into `per_bug_type.json`. The script verifies all 84 report hashes against `sealed_reports.json` with the evaluator's
  own hashing (`evaluation/run.py:229`). Exact bug parameters stay in the evaluator's private record.
- "Output relative L2" for planted bugs is ||candidate - reference|| / ||reference|| over each case's whole output
  tensor (all evaluation tokens of that case), as routediff reports it; the table gives the median over the 4 cases.
  Element ULP is reported in the findings but is dominated by near-zero outputs.
